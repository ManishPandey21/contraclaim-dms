# Skill-pack golden sets (4B-42)

Plan reference: `docs/superpowers/specs/2026-11-16-claim-bench-phase-4b-hardening.md`, section 7 (requirements), D-21 and AQ-10 (store and budget). The server-side runner that uses these sets is 4B-41 (`services/skills/evaluation.py`).

A run on a synthetic set is made, kept and shown like any other, but it records `suite_ready: false` and approval and publication refuse it (409 `eval_suite_not_ready`). No pack is published in Phase 4b.

## Where sets live

- **Real sets:** the restricted, encrypted evaluation store outside the repository (AQ-10). The server reads `SKILL_EVAL_SUITE_DIR/<skill_key>.json`; a key cannot reach outside that directory. Only hashes of real sets are recorded in the repository.
- **Synthetic sets:** `backend/rbac_backend/skill_eval/synthetic/<skill_key>.json`, generated by `scripts/build_synthetic_golden_sets.py` (the test suite fails if a committed file differs from the generator's output). Every matter is invented.

## File format

One JSON object per pack: `suite_key`, `skill_key`, `prompt_key` and `matters`. Each matter has:

- `matter_id` and `role`: the party the skill acts for;
- `payload`: the prompt inputs the pack's prompt takes:
  - claims (`claims.v1.head_test`): `facts`, `title`, `kind`, `event_summary`, `clauses`;
  - EOT (`letter_drafting.v3.skill_step`): `task`, `subject`, `contract_form`, `material`, `sources`, `inputs`;
- `record`, for the hard gates:
  - `clauses`: the clauses the matter contains;
  - `notice_days`: the notice periods its contract states;
  - `privileged_markers`: passages from its privileged material that must never appear in an output;
- `labels`:
  - `elements`: element to adjudicated state;
  - `classification`: `{field, expected}`;
  - `information_required`;
- `composition`: the tags below;
- `provenance`:
  - `source`: `synthetic`, `anonymised_real` or `expert_written`;
  - `labelled_by`: the two experts;
  - `adjudicated_by`: the legal approver;
  - `disagreements`: the labels the experts differed on;
  - `consent_reference`: required for `anonymised_real`.

The set's identity is the SHA-256 of its canonical JSON. A run records it, and a change to the set makes every earlier run stale.

## Rules a set must meet to support an approval (`suite_problems`)

**Claims, 15 matters:**
- at least 4 from the Engineer's or the Employer's position, counted by role;
- 3 `late_notice`, of which at least 1 is `late_notice_with_prejudice` and 1 is `late_notice_without_prejudice`;
- 2 `global_claim`;
- 2 `missing_records`;
- 2 `variation_derived`;
- 2 `straightforward`.

**EOT, 15 matters:**
- 4 `true_concurrency`;
- 2 `neutral_event`;
- 2 `superseded_determination`;
- 2 `no_critical_path_proof`;
- 2 `windows_method`.

**Every matter:**
- not synthetic;
- labelled by two distinct experts;
- adjudicated by a third person (the legal approver);
- an anonymised real matter names the owner's consent.

## Gates applied to a run (4B-41, plan section 7)

**Hard gates** (any failure fails the run):
- a figure not in the matter;
- a notice period the contract does not state;
- a clause not in the matter;
- a privileged passage in the output;
- a schema failure.

**Scored gates:**
- element agreement at the configured threshold (at least 0.85);
- each element type at 0.75;
- classification at 0.85;
- degraded steps at most 5 %.

## What remains to build a real set

1. The reviewing experts write or select the matters. Anonymised real matters need the owner's consent.
2. Two experts label each matter independently.
3. The legal approver adjudicates disagreements.
4. The set is placed in the evaluation store, and `scripts/skill_golden_set.py check` passes on it.
5. Its hash is recorded in this document.
6. A run is made on the server, and its report is reviewed matter by matter.
