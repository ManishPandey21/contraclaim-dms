# FalkorDB Reference-Link Audit

## Purpose and Scope

This audit explains how correspondence letters are stored, linked, referenced, updated, searched, and validated in the current codebase, with special focus on FalkorDB. The request used `falkrdb`; this document treats that as FalkorDB, the graph database integration implemented through the Redis protocol.

In this system, "letters" appear in two related forms:

- Uploaded correspondence documents in MongoDB `documents`, including incoming/outgoing PDFs and their extracted metadata.
- Workflow/drafting records in MongoDB `letters`, used by the letter workflow and AI drafting pipeline.

MongoDB is the system of record for document metadata, letter records, parsed references, manually linked references, and bidirectional `references` / `referencedBy` links. FalkorDB is an optional traversal graph used to represent normalized letter-code relationships as `Letter` nodes connected by `CITES` and `REPLIES_TO` relationships.

## Current State Verdict

FalkorDB is optional and feature-flagged. If `FALKORDB_ENABLED` is false, FalkorDB writes and reads become no-ops, while MongoDB document storage and reference links continue to work.

MongoDB remains authoritative for uploaded documents and bidirectional document links. FalkorDB stores a derived graph keyed by normalized letter codes and is used for traversal context in drafting and reporting, not as the only search or persistence path.

The historical Graphiti/Falkor coupling has been addressed in current code: `GraphIngestionService` skips Graphiti upserts when the Graph adapter is disabled but still calls FalkorDB sync. This is visible in `GraphIngestionService._ingest_document_sync`, which logs that Graphiti is skipped while Falkor sync continues.

## Data Model and Storage

### MongoDB `documents`

Uploaded correspondence is stored in the `documents` collection. The document model includes:

| Field | Role |
| --- | --- |
| `letterNo` | Human-facing letter/reference number. |
| `letterNoNormalized` | Normalized code generated by `normalize_letter_code`; used for matching references. |
| `reference` | Parsed metadata references extracted from OCR/LLM processing. These are not necessarily resolved to documents. |
| `references` | Forward links from this document to resolved target documents. |
| `referencedBy` | Backlinks from target documents to documents that reference them. |
| `organization_id`, `project_id` | Tenant/project scope fields. |
| `uploadType` | Usually `incoming`, `outgoing`, or `contract`. FalkorDB maps only incoming/outgoing letter direction. |
| `processing_status`, `metadata_source`, `processing_metadata` | Processing state and extraction provenance. |

`DocumentService.create_document` sets `letterNoNormalized` when an uploaded document already has `letterNo`. During processing, `DocumentService.process_document_async` can overwrite `letterNo`, recompute `letterNoNormalized`, store parsed metadata references, run graph ingestion, and then run reference sync.

Mongo indexes include wildcard text search and scoped indexes for `organization_id`, `project_id`, `letterNoNormalized`, and `letterNo` in `core/database.py`.

### MongoDB `letters`

The `letters` collection stores workflow and drafting records. The model includes:

| Field | Role |
| --- | --- |
| `letter_no` | Workflow letter number. |
| `reference` | Single legacy/reference object for a letter. |
| `references` | Conversation references, either internal `letter_id` or external `letter_no`. |
| `previous_letter_id` | Conversation/thread parent. |
| `conversation_id`, `thread_id`, `thread_letters` | Conversation and thread grouping. |
| `graph_thread` | Stored graph context snapshot from drafting runs. |
| `context_document_ids`, `context_documents`, `draft_sources` | Downstream drafting context and evidence. |

The `letters` collection is indexed by organization, project, conversation, previous letter, status, and timestamps. It does not replace document storage; it supports drafting workflow state.

### FalkorDB `Letter` Nodes

`FalkorGraphService.upsert_letter_with_refs` writes `Letter` nodes with a normalized key:

| Property | Source/Meaning |
| --- | --- |
| `normCode` | Normalized stable key from `normalize_letter_code`. |
| `code` | Original letter/reference code where available. |
| `direction` | `incoming`, `outgoing`, or `unknown` for placeholder referenced nodes. |
| `subject` | Subject/title when available. |
| `date` | Date formatted as string. |
| `organization_id`, `project_id` | Scope metadata when available. |
| `project` | Legacy project display/fallback field. |
| `createdAt`, `lastUpdated` | Falkor write timestamps. |

The service ensures indexes on `Letter.date`, `Letter.direction`, `Letter.organization_id`, and `Letter.project_id`. It does not currently ensure an index on `Letter.normCode`, even though all upsert and traversal paths are keyed by `normCode`.

### FalkorDB Relationships

FalkorDB stores two letter-to-letter relationship types:

| Relationship | Meaning | Writers |
| --- | --- | --- |
| `CITES` | A letter/document cites or references another letter/document. | Parser metadata, manual/document links when synced, agent-selected drafting context. |
| `REPLIES_TO` | A letter replies to or follows another letter. | `previous_letter_id` and explicit `REPLIES_TO` reference payloads. |

Relationships carry `source`, `createdAt`, and `updatedAt`. Parser/null relationships can be cleaned before reinsertion when `FALKORDB_CLEANUP_REFERENCES` is enabled.

## Reference Relationship Creation and Maintenance

### Parser References

Parser references originate from OCR/metadata extraction. The processing path normalizes these references through `DocumentService._normalize_metadata_references` and stores them in the document `reference` field.

After the document record is updated, `ReferenceSyncService.sync_bidirectional` processes the parsed references with `source="parser"`:

1. Validate the source document id.
2. Normalize each reference payload.
3. Resolve the target by `documentId` where present.
4. Otherwise resolve by `letterNoNormalized`.
5. Fall back to case-insensitive exact `letterNo` matching.
6. Write resolved target links to the source document `references`.
7. Write backlinks to target documents `referencedBy`.
8. Queue unresolved references in `reference_sync_queue`.

The source bucket is replace-style by `source`: parser-sourced links are recalculated from the current parser reference set, while non-parser/manual links are preserved.

### Manual References

Manual references are exposed through:

- `GET /documents/{id}/references`
- `POST /documents/{id}/references`
- `DELETE /documents/{id}/references/{reference_id}`
- `POST /documents/link`
- `GET /documents/{id}/linked`

`DocumentService.add_reference` resolves the target document first, prevents self-reference, builds a manual `DocumentReference` payload, and calls `sync_bidirectional` with `source="manual"`. `DocumentService.link_documents` is a wrapper around `add_reference`.

Important behavior: because `sync_bidirectional` replaces the current source bucket for the provided `source`, sending only one manual payload can cause prior manual links on the same source document to be removed. Parser sync avoids this by replaying the full parser set. Manual add should do the same or use append/merge semantics.

### Missing References and Reaper

Unresolved parser references are inserted into `reference_sync_queue` with `status="pending"`. The scheduled `reference_sync_reaper`:

- Expires stale pending entries after the configured TTL.
- Marks entries orphaned when the source document no longer exists.
- Replays the source document parser reference set plus queued references.
- Marks entries resolved if their target document has since been ingested.

The scheduler wraps jobs in a leader lock, so the reaper is intended to run once across replicas when enabled.

### FalkorDB Graph Maintenance

`GraphIngestionService.sync_document_to_falkor` builds a Falkor payload from:

- Document `letterNo`, `letter_no`, `code`, or fallback `document_id`.
- Metadata `letter_no`, subject, date, and references.
- Document `reference`, `references`, and `previous_letter_id`.

Falkor references are deduplicated by normalized code and relationship type. Target nodes are created as placeholder `Letter` nodes if only a reference code is known.

If cleanup is enabled, `upsert_letter_with_refs` deletes parser/null `CITES` and `REPLIES_TO` outgoing relationships from the source node before reinserting current parser edges. Agent writes pass `cleanup=False`, so selected drafting context is additive.

## Updates and Consistency

| Update path | Mongo behavior | FalkorDB behavior | Consistency note |
| --- | --- | --- | --- |
| Metadata processing | Updates metadata, normalized letter code, parsed references, and graph. | Yes, via graph ingestion. | Strongest automatic consistency path. |
| Explicit sync endpoint | Replays parser links. | Yes, calls Falkor sync. | Useful repair path. |
| Manual add reference | Updates Mongo `references`/`referencedBy`. | No guaranteed immediate graph sync. | Should resync Falkor after mutation. |
| Manual remove reference | Removes Mongo manual link/backlink. | No guaranteed graph edge cleanup. | Can leave stale Falkor relationship. |
| Document metadata edit | Recomputes `letterNoNormalized` when `letterNo` changes. | No automatic Falkor sync in `update_document`. | Can leave stale `normCode`/edge data. |
| Soft delete | Sets document `lifecycle_state="deleted"`. | No direct graph cleanup. | References and graph nodes can remain unless reconciled. |

## Search, Retrieval, and Downstream Use

### MongoDB Search

`/search/documents` uses Mongo aggregation over the `documents` collection. It supports text search through the wildcard text index, RBAC scoping, date filters, upload direction, tags, organization, and project filters.

Exact reference search in the drafting service searches:

- Document `letterNo`
- Document `letter_no`
- Document `letterNoNormalized`
- Document `references.letterNo`
- Document `references.letter_no`
- Letter `letter_no`
- Letter `letterNo`
- Letter `reference`
- Letter `previous_letter_no`

This means exact reference lookup does not depend on FalkorDB.

### FalkorDB Traversal

`FalkorGraphService.get_thread(norm_code, depth)` returns the root letter plus neighbors connected through `CITES` or `REPLIES_TO` relationships. Depth zero is specially handled to avoid invalid variable-length path expressions.

`FalkorGraphService.get_neighbors(norm_code, direction)` returns outgoing or incoming neighbors. Read-only Cypher is routed to `GRAPH.RO_QUERY`; writes go to `GRAPH.QUERY`.

### Drafting and LangGraph

The letter drafting context service uses FalkorDB only when enabled and a target letter code exists. It calls `get_thread(target_code, depth=6)` and converts graph nodes into `graph_thread` source evidence.

The LangGraph letter pipeline also reads graph threads for context. During finalization, it may write agent-selected context documents as `CITES` edges with source `agent`, then refresh the graph thread. Those agent edges are additive because cleanup is disabled for that write.

### Reports

The linked-letter-chain report requires FalkorDB. It traverses either downstream:

```cypher
(root)-[:CITES|REPLIES_TO*1..5]->(node)
```

or upstream:

```cypher
(node)-[:CITES|REPLIES_TO*1..5]->(root)
```

The report then enriches returned graph rows from MongoDB `documents` and `letters` using raw and normalized letter codes.

## Observed Risks and Improvement Recommendations

| Priority | Finding | Impact | Recommended improvement |
| --- | --- | --- | --- |
| High | FalkorDB schema does not ensure an index on `Letter.normCode`. | Upserts and reads depend on `normCode`; graph operations can degrade as data grows. | Add `CREATE INDEX FOR (n:Letter) ON (n.normCode)` or Falkor-compatible equivalent in `ensure_schema`. |
| High | Reference resolution by `letterNoNormalized` is not visibly scoped by source organization/project. | Duplicate letter numbers across projects/tenants can link to the wrong document. | Pass source org/project into `_resolve_target_document` and include it in normalized/code matching. |
| High | Manual `add_reference` sends only the new manual reference into a replace-style source bucket. | Adding a second manual reference can remove earlier manual links. | Change manual add to merge with existing manual references or replay the full manual set plus the new link. |
| High | Manual add/remove does not consistently update FalkorDB. | Mongo and Falkor can diverge; reports/drafting graph context can show stale or missing edges. | Call `sync_document_to_falkor` after successful manual add/remove and after link endpoint mutations. |
| Medium | `update_document` recomputes `letterNoNormalized` but does not resync FalkorDB. | Edited letter numbers or metadata can leave stale Falkor `normCode` nodes and relationships. | Resync Falkor when `letterNo`, `reference`, `references`, `previous_letter_id`, org, or project changes. |
| Medium | Soft-deleted documents are not removed from FalkorDB or backlinks. | Deleted documents may still appear in graph traversal or reference contexts. | Add deletion reconciliation or filter/enrichment logic that excludes deleted Mongo documents. |
| Medium | Parser cleanup deletes outgoing parser/null Falkor edges only when ref list exists. | If parser references become empty, old parser edges may remain. | Run cleanup when cleanup is enabled even if the new reference list is empty. |
| Medium | Placeholder target nodes can lack org/project metadata. | Traversal filters intentionally allow null org/project nodes, which can broaden results. | Backfill placeholder nodes when target documents are later resolved; include scope on placeholder creation where known. |
| Low | Mongo `documents` does not enforce unique `letterNoNormalized` per org/project. | Multiple documents can share one normalized code; sometimes valid, sometimes ambiguous. | Decide business policy; add partial unique index only if one canonical document per letter number is required. |
| Low | FalkorDB graph has no built-in reconciliation report against Mongo `references`/`referencedBy`. | Drift is hard to detect. | Add admin reconciliation tooling comparing Mongo links with Falkor `CITES`/`REPLIES_TO` edges. |

## Responsibility Matrix

| Responsibility | MongoDB | FalkorDB |
| --- | --- | --- |
| Authoritative document metadata | Yes | No |
| Authoritative uploaded file/document record | Yes | No |
| Parsed reference text from OCR/LLM | Yes, `reference` | Derived only |
| Resolved source/target document links | Yes, `references` and `referencedBy` | Derived edges |
| Fast graph traversal by letter code | Limited/manual query | Yes |
| Drafting graph context | Stored snapshots and source ledger | Traversal source |
| Linked-chain reports | Enrichment and fallback metadata | Primary traversal |
| Tenant/project scoping | Primary fields and indexes | Metadata properties, but not consistently guaranteed on placeholders |

## Bottom Line

The reference-link implementation has a workable split: MongoDB owns durable records and resolved bidirectional links, while FalkorDB provides graph traversal over normalized letter codes. The strongest path is automatic metadata processing, which updates Mongo metadata, writes Falkor nodes/edges, and synchronizes parser references.

The main consistency gaps are around mutation paths outside processing: manual links, metadata edits, soft deletes, and empty-reference cleanup. The most important fixes are to scope reference resolution by org/project, preserve existing manual links during manual add, index `Letter.normCode`, and resync/reconcile FalkorDB after user-managed reference mutations.
