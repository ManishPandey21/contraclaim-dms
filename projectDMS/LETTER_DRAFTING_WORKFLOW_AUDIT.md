# Letter Drafting Workflow Audit

Date: 2026-05-22

## Scope

This audit maps the implemented workflow from incoming letter/request through strategy planning, AI drafting, review, approval, export, and issue. It focuses on the required strategic-plan roadmap and the ten critical/high-priority workflow gaps listed in the correction instructions.

## Actual Workflow Map

1. Letter/request is created in `letters` with status metadata, parties, subject, content, references, context documents, and strategy/draft fields.
2. Drafting session starts through `/letter-drafting/start` or directly through `/letters/{letter_id}/drafting/*`.
3. Incoming analysis is created by `/analyze-incoming`, which runs a background `DraftRun`.
4. Strategy plan is generated by `/prepare-plan`, creating a `letter_draft_runs` record in `strategy` mode.
5. Plan confirmation can update the planning sheet and reply matrix through `/runs/{run_id}/confirm-plan`.
6. Draft generation uses `/generate-draft`, creating a `draft` mode run with a draft artifact, source ledger, validation report, cyclic trace, assertion support, and confidence scores.
7. Reviewer assignment and comments are handled through `/assign-reviewer` and `/comments`, persisted in governance collections.
8. Review validation and critique are available through `/validate` and `/critique`.
9. Approval runs `/approve`, which accepts the draft as a letter draft version and marks the run approved.
10. Export creates immutable DOCX/PDF file object references.
11. Issue requires exported artifacts and records the issued-letter metadata.

## Strategic Plan Roadmap Audit

### Incoming Letter Analysis

Before fixes, incoming analysis extracted only a small subset: letter number, date, subject, main request, cited clauses, amount, requested action, deadline, and a broad risk label. It did not persist sender role/party type, issue classification source/editability, subject matching, deadline alert metadata, or clause evaluation rows.

After fixes, `IncomingLetterAnalysis` captures:

- Sender/entity and sender role or party type.
- Letter/reference number, date, recipient, subject, and contract/project reference.
- Whether the extracted subject appears to match the requested matter.
- Issue classification with source (`manual`, `ai`, or `system_default`) and editable flag.
- Requested action, response requirement, stated deadline, contractual response period, deadline risk, immediate action, priority flag, drafter/reviewer alerts, approval urgency, and workflow due date.
- Cited clause numbers plus a reviewable `CitedClauseEvaluation` structure.

### Issue Classification

Before fixes, issue type was inferred only indirectly through `letter_category`. It was not saved in the strategic plan or reviewable as a separate field.

After fixes:

- `DraftRunCreateRequest.issue_type` allows manual issue selection.
- Incoming analysis detects issue type from letter text when not manually supplied.
- Planning sheet saves issue type.
- Plan text includes issue type and uses it in risk/deadline context.

### Requested Action And Deadline

Before fixes, deadline handling was minimal and did not drive priority, alerts, approval urgency, or workflow due date fields.

After fixes:

- Deadline phrases such as `within 7 days`, `by DD/MM/YYYY`, and `on or before DD/MM/YYYY` are detected.
- Deadline risk, priority flag, drafter alert, reviewer alert, approval urgency, and workflow due date are persisted in analysis.
- Planning sheet includes response deadline and deadline risk.

### Cited Clauses

Before fixes, cited clause numbers were extracted, but clause evaluation was not represented as a first-class object and strategic planning did not show clause verification status.

After fixes:

- Cited clauses are normalized and stored.
- Each cited clause gets a reviewable evaluation row with existence, quote match, applicability, sender reliance, counter-clauses, position effect, and legal/commercial review flags.
- Strategic plan text includes a cited clause checks section.

Remaining limitation: exact contract cross-checking still depends on retrieved `contract_clause` sources. Automated clause existence and quote-match values are intentionally left nullable when the contract source is not available.

### Strategic Plan Prompt Review

Before fixes, the default strategy prompt in `backend/rbac_backend/services/letter_drafting/prompts.py` instructed the AI to return only five sections:

- Tone and posture.
- Facts to rely on.
- Contractual references to verify.
- Drafting sequence.
- Open confirmations.

That prompt did not require the AI to produce the required roadmap before drafting a response letter. It also did not explicitly instruct the AI to verify sender/subject, reference/date, issue type, requested action, stated deadline, contractual response deadline, clause correctness, clause applicability, counter-clauses, missing information, manual drafter checks, or suggested reply structure.

After fixes:

- `DEFAULT_STRATEGY_TEMPLATE` now requires exactly the 15 roadmap sections.
- `PromptRegistry.get_enabled()` now applies `ensure_strategy_roadmap()` to enabled database prompt overrides, so a custom DB prompt cannot silently omit the required roadmap.
- `fallback_strategy_plan()` now returns the same 15-section roadmap if the LLM call fails.
- Tests verify the default prompt and DB-override addendum include every required roadmap section.

Prompt roadmap compliance after fixes:

## Root Cause Findings

| Gap | Root Cause | Fix Status |
| --- | --- | --- |
| Missing required inputs before strategic plan generation | Threshold validation existed, but roadmap fields were not modeled and draft mode could generate a new plan implicitly. | Fixed for backend model, analysis, planning, and draft blocking without a saved/latest plan. |
| Strategic plan not saved or reused correctly | `/prepare-plan` returned a plan but did not persist it as the latest governed strategy version. | Fixed. Generated and confirmed plans are saved on the letter and versioned. |
| AI drafting not using saved/latest strategic plan | Draft run used override or `letter.strategy_plan`, then generated a plan if missing. | Fixed. Draft mode resolves override, saved letter plan, or latest strategy run; otherwise blocks. |
| Drafter/reviewer comments not captured | Governance comments were persisted but not fed into subsequent draft context. | Fixed. Latest governance comments are injected into context and source ledger for subsequent runs. |
| Invalid workflow transitions | Some lifecycle actions were permissive, especially assignment/approval. | Partially fixed. Reviewer assignment and approval now reject blocked/failed/finalized invalid states. |
| Missing role checks | Route policy checks existed, but reviewer assignment and reviewer-only actions lacked run-level checks. | Partially fixed. Assigned reviewer restrictions added for comments/returns; self-approval remains blocked except admin. |
| Missing approval audit trail | Events existed but lacked approved-version lock payload. | Fixed. Approval event records approved draft version when lock succeeds. |
| Missing version history for strategy and drafts | Draft versions existed; strategy versions did not. | Fixed. Added strategy versions and draft lock metadata. |
| AI review not checking draft against strategy | Validator checked source/clause support but not strategy alignment. | Fixed. Validation/critique now require a strategy plan and warn on weak draft-plan alignment. |
| Final approval not locking approved version | Approval accepted draft but did not mark approved snapshot locked. | Fixed. Approval locks the accepted draft version and writes approved-version fields on the letter. |
| Strategic plan prompt missing roadmap sections | Default prompt only asked for five generic sections, and DB prompt overrides could omit roadmap requirements. | Fixed. Default prompt, DB override addendum, fallback plan, and tests now enforce the 15-section roadmap. |

## Code Fix Summary

Backend changes:

- Added strategic roadmap fields to `DraftRunCreateRequest`, `IncomingLetterAnalysis`, and `PlanningSheet`.
- Added `CitedClauseEvaluation`.
- Added `StrategyVersion` and approved-draft lock metadata to `Letter`.
- Expanded incoming analyzer to extract sender, subject, contract reference, issue type, deadlines, priority fields, and cited clause evaluation rows.
- Expanded deterministic plan text to include issue type, deadline, and cited clause checks.
- Added strategy plan saving/versioning in `DraftRunRepository`.
- Added approved draft locking in `DraftRunRepository`.
- Changed draft creation behavior to block when no saved/latest strategy plan exists.
- Reused latest strategy run when no accepted letter plan exists.
- Injected latest governance comments into subsequent draft source context.
- Added strategy-alignment validation to draft validate/critique/cyclic review.
- Tightened reviewer assignment, reviewer comment/return, approval, and self-approval checks.
- Enforced the 15-section strategic-plan roadmap in default prompts, DB prompt overrides, and fallback strategy plans.

Tests added/updated:

- Incoming analyzer roadmap extraction.
- Strategy prompt roadmap enforcement.
- DB prompt override roadmap addendum.
- Strategy alignment blocking when plan is missing.
- Strategy version persistence.
- Approved draft version locking.
- Existing draft immutable version test updated to assert version number.

## Production Readiness Score

Before improvements: 58/100

Reasons:

- Strategy plan persistence depended too heavily on UI save behavior.
- Draft generation could proceed without a clearly saved strategic plan.
- Strategy version history was missing.
- Approval did not lock a final approved draft version.
- AI review did not explicitly compare against strategy.
- Roadmap analysis fields were incomplete.

After improvements: 79/100

Remaining production risks:

- Clause existence, quote-match, and counter-clause checks need deeper integration with exact contract clause retrieval.
- Frontend should expose all new roadmap fields and prompt-derived sections for drafter edit/comment, not only consume backend data.
- Workflow should eventually enforce a formal submitted-for-review state instead of allowing direct approval by an approver with permission.
- Migration/backfill is needed for existing letters without `strategy_versions`, `approved_draft_version`, or `approved_version_locked`.
- End-to-end API tests should be added with real policy service and Mongo integration.

## Phase-Wise Implementation Plan

### Phase 1: Critical Backend Governance

Status: Implemented.

- Block AI drafting when no strategic plan is available.
- Save and version generated/confirmed strategy plans.
- Reuse saved/latest strategy plan during drafting.
- Capture comments into subsequent draft context.
- Lock approved draft version.
- Add audit payloads for versioned strategy/draft events.

### Phase 2: Roadmap Completeness

Status: Partially implemented.

- Add UI controls for issue type, response deadline, sender role/party type, subject match, and cited clause evaluation.
- Allow drafter comments against cited clause evaluation rows.
- Render all 15 strategic-plan prompt sections as structured fields where possible.
- Add reviewer/approver deadline alerts and due-date workflow widgets.

### Phase 3: Contract Clause Verification

Status: Planned.

- Use exact clause retrieval to set `exists_in_contract`.
- Compare cited quote text with contract text.
- Detect related/counter clauses.
- Flag legal/commercial review when clause reliance is weak or high-risk.

### Phase 4: Workflow State Machine

Status: Planned.

- Add explicit statuses for `strategy_saved`, `draft_generated`, `submitted_for_review`, `review_returned`, `review_cleared`, `approved_locked`, `exported`, and `issued`.
- Enforce transitions in one service-level state machine.
- Add integration tests for every allowed and rejected transition.

### Phase 5: Migration And Observability

Status: Planned.

- Backfill strategy versions from existing `strategy_plan`.
- Mark existing approved/current draft versions where approval metadata is present.
- Add dashboard metrics for missing strategy, unverified clauses, overdue response deadlines, and approval-lock compliance.

## Final Launch Recommendation

Recommendation: Do not launch as fully production-ready yet.

The workflow is now acceptable for controlled pilot use with backend safeguards enabled, but production launch should wait until Phase 2 and Phase 3 are complete. The main remaining launch blocker is clause verification: the strategic plan can store clause checks, but it does not yet reliably prove cited clauses exist, are quoted correctly, or are applicable unless retrieval sources are already available.

Pilot recommendation:

- Enable for a small internal drafting/review group.
- Require human review for all high-risk issue types: claim, delay, variation, payment, and dispute.
- Do not allow issued letters without exported DOCX/PDF artifacts and approved-version lock.
- Review audit logs weekly during pilot.
